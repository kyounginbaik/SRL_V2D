EXPERIMENT CONTRACT

- Full training: 100,663,296 environment steps; 2,048 training worlds.
- Upper search: 2,048 candidate slots, one world per candidate, every 501,760
  steps (~500K). This budget is shared across the selected local windows; it
  is not 2,048 candidates for each window. A no-edit control is included.
- Lower policy: full-hand FlashSAC, 56 action dimensions, finger PCA exploration.
- Upper edits: local 56D wrist-and-finger corrections for both hands. Windows
  are selected from observed failure/onset, not predefined task stages.
- Upper ablation: independent Gaussian proposals versus learned FlashSAC
  proposals. Every candidate gets its solved convex lower policy-head response.
- Training resets: exact frame-zero wrist/finger joints and object poses,
  zero velocities. No random reset frame or sampled finger opening. SAC action
  exploration and seed-dependent learning/proposals remain enabled.
- Failure detection: one deterministic, unperturbed VOC=0 baseline rollout.
  First sustained failure of any object guides window selection.
- Acceptance: local pose/wrench improvement around the failure, both-object
  guards, and protection of the saved successful prefix. No three-perturbed-
  initial-state confirmation veto.
- Save matched reference/actor pairs. training/best_demo.json points to the
  preferred archived pair. A regressed checkpoint cannot overwrite that pair;
  the active training learner can still regress and is not automatically reset.
- Object masses: pot 0.2 kg; lid/spoon 0.1 kg. Use the bundled meshes/inertias.
- Wrist controller: kp=100, kd=12, effort limit=90; no additional speed cap.
- Rewards: hand keypoint tracking weight=2; finger-joint tracking weight=0.25.
- VOC starts at 1.0 and decreases by performance gates, not elapsed time.
  Upper scoring and main physics/Track3 estimates use VOC=0.
- Checkpoint/media interval: 1,003,520 steps, plus final save. Preserve video
  history and reference overlays with original hands at 45% opacity.
- The full phase is called "pilot" in output paths/W&B for compatibility.
  This label does not imply a short run: its budget is 100.7M steps.

Preserve these settings. Adapt paths, scheduler options, GPU assignment and
logging credentials to this server. Do not silently reduce world/candidate
counts, change dependencies, substitute reconstructed inputs, or revert to
older randomized-start/consensus16 configurations to make a run fit.

SETUP

1. Inspect the host before reserving resources:

   nvidia-smi
   docker version
   git lfs version

   The pinned JAX CUDA 13 environment needs a compatible NVIDIA driver >=580.
   The original cluster uses L40S 48GB and B200 GPUs. Reserve one GPU, 12 CPUs
   and 96GB host RAM per full run. A fresh Docker build also needs substantial
   disk space; inspect free space before building. On a managed cluster use
   its scheduler for GPU checks/training. Do not upgrade shared drivers or
   change the method to bypass an incompatible host; report the actual blocker.

2. Clone into a new directory. Use existing GitHub authentication; HTTPS or SSH
   is fine. Avoid changing another working checkout:

   GIT_LFS_SKIP_SMUDGE=1 git clone git@github.com:kyounginbaik/SRL_V2D.git SRL_V2D_fixed_start
   cd SRL_V2D_fixed_start
   GIT_LFS_SKIP_SMUDGE=1 git checkout --detach d9a72f5432c02e3e35eadfcd49cffe58e2b0e8c5
   git lfs install --local
   git lfs pull --include='robotic_grounding/uniretarget/**,robotic_grounding/flash_chord/src/flash_chord/assets/**' --exclude=''

   This selective download includes approximately 0.42 GiB of LFS objects;
   Git history and Docker layers are additional. No recursive submodule setup
   or download of unrelated reconstruction models is required. This handoff
   was added after the implementation commit; retain the instructions outside
   the checkout if needed before checking out that exact commit.

3. Build the two images from the pinned lockfile. Run from the repository root:

   docker build -f robotic_grounding/flash_chord/docker/Dockerfile \
     -t flash_chord:chord100m-base robotic_grounding/flash_chord
   docker build -f robotic_grounding/uniretarget/Dockerfile.media \
     -t uniretarget:chord100m robotic_grounding/uniretarget

   Host Python only needs the standard library; the scientific dependencies
   are inside Docker. Do not replace the locked stack with pip's latest versions.

4. Configure W&B using credentials already available on this server. Do not
   copy another server's credentials or embed keys in files/commands/reports.

   export WANDB_MODE=online
   export WANDB_ENTITY=DexDreamer
   export WANDB_PROJECT=v2d-track3-uniretarget

   WANDB_API_KEY must be provided securely through the environment for online
   logging. If the intended account uses a private W&B endpoint, also set
   WANDB_BASE_URL to that actual endpoint. The launcher forwards these variables.
   Without online configuration, portable runs default to offline logging and
   will not appear in the web UI. Report that distinction clearly.

   Leave UNIRETARGET_RUN_TAG unset to use the automatic hostname/output-path
   hash, or set a NEW tag containing this server, experiment and upper mode.
   Never reuse the original cluster's chord-fixed-start-*-20261015 run IDs.
   The run ID also includes phase, episode and seed; ensure gaussian and
   flashsac have different tags if specifying tags explicitly.

5. Prepare the input bundle for both modes (no GPU required):

   python3 robotic_grounding/uniretarget/launch.py --prepare-only --upper gaussian
   python3 robotic_grounding/uniretarget/launch.py --prepare-only --upper flashsac

   Defaults: REPO/.uniretarget/chord-fixed-start-gaussian and
   REPO/.uniretarget/chord-fixed-start-flashsac. An absolute --run-root can
   select other storage; use separate roots for the two upper modes.
   Preparation validates input hashes and relocates asset paths. It rejects
   changed code/inputs in a previously prepared root. Keep this checkout fixed
   during training; use a fresh root for changes or a retry after training starts.

GPU VALIDATION AND SINGLE-JOB COMMANDS

Use an allocated GPU UUID or its host index. Replace GPU_UUID_OR_INDEX below
with the actual allocated device; the launcher exposes exactly that GPU.

   python3 robotic_grounding/uniretarget/launch.py \
     --episode 1 --seed 43 --upper gaussian --phase smoke --gpu GPU_UUID_OR_INDEX

search at 32,768. It runs targeted CPU tests first, then GPU training, reference
search, initial-state audits, archive checks, physics rendering, and W&B sync.

After that successful smoke, run its corresponding full training without

SLURM ALTERNATIVE

The portable script is robotic_grounding/uniretarget/train.sbatch. It accepts
EPISODE SEED UPPER and always uses phase full. It requests one GPU, 12 CPUs,
96GB RAM, 40 hours. Submit from the cloned repository root. Override the local
partition/account/time as needed; do not use node01/node100/node200 names from
the original cluster. Keep outputs in a persistent local directory.

After smoke validation, a clean full-batch example is:

   mkdir -p slurm_logs
   for upper in gaussian flashsac; do
     for episode in 1 3 5 6 35; do
       for seed in 43 44 45; do
         sbatch --partition=YOUR_PARTITION \
           --job-name="fixed-${upper}-e${episode}-s${seed}" \
           --output="slurm_logs/%j.out" --error="slurm_logs/%j.err" \
           robotic_grounding/uniretarget/train.sbatch "$episode" "$seed" "$upper"
       done
     done
   done

smoke used the default gaussian root, submit episode1/seed43/gaussian separately

loop. Alternatively run the initial validation in a separate --run-root, then
use the untouched default roots for all 30 full jobs. Preserve distinct W&B run
IDs for validation and production. Do not submit duplicate episode/seed/mode jobs.
If you queue production before validation finishes, use afterok dependencies
and fail/cancel dependents if validation fails. Keep a manifest of all job IDs,
episode/seed/mode, output roots, code commit, image IDs and W&B URLs.
